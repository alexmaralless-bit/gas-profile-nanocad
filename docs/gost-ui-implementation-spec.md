# Спецификация доведения UI профиля до ГОСТ

Цель: привести чертеж продольного профиля газопровода к виду ГОСТ 21.710-2021, форма 1 и пример Б.1, без потери инженерной редактируемости.

## Связь с roadmap

Этот документ детализирует активный этап `Этап 6. ГОСТ UI профиля` из `docs/roadmap.md`.

Если roadmap и эта спецификация расходятся в деталях текущей UI-фазы, приоритет имеет эта спецификация. Roadmap описывает общий продуктовый порядок, а этот документ - конкретные сессии генерации кода.

## Текущие команды и ограничения

Основные команды, которые должны сохранять работоспособность после каждой сессии:

- `GASPROF_DRAW_DRAFT` - первичное построение чернового профиля;
- `GREC` / `GASPROF_RECALC_PROFILE` - пересчет таблицы по отредактированной проектной трубе;
- `GASPROF_RECALC_CASINGS` - актуализация футляров;
- `GASPROF_ADD_SITUATION` - добавление ситуации;
- `GVAL` / `GASPROF_VALIDATE` - валидация;
- `GPIPE` / `GASPROF_CHECK_PIPE` - диагностика проектной трубы.

Текущие данные профиля:

- связь профиля с трассой и поверхностью хранится в XData проектной трубы;
- актуальная версия XData: `GASPROF_PIPE_PROFILE_V5`;
- сессионные объекты таблицы/развернутого плана удаляются по XData `GASPROF_ENTITY`;
- футляры на плане могут иметь атрибуты `START_CHAINAGE`, `END_CHAINAGE`, `CENTER_CHAINAGE`, `LENGTH`, `GEOM_SIGNATURE`;
- дно траншеи считается как `верх трубы - наружный диаметр трубы - песчаная подушка`.

Ограничение текущей UI-фазы: не менять расчетное ядро TIN и не ломать существующий рабочий цикл ради оформления. Все изменения должны быть совместимы с ручным редактированием проектной трубы.

## Общий критерий готовности сессии

Каждая сессия считается завершенной, если:

- проект собирается через `build.ps1`;
- DLL можно загрузить через `NETLOAD`;
- `GASPROF_DRAW_DRAFT` и `GREC` не теряют основной сценарий;
- новые объекты получают XData для последующего удаления/перестроения;
- результат можно проверить визуально на демонстрационном чертеже (в репозиторий не входит);
- изменения не требуют ручной чистки DWG между нормальными пересчетами, кроме случаев полной новой отрисовки профиля.

## Сессия 1. Разделить типы станций

Статус: реализовано в коде MVP.

Задача: убрать перегруз таблицы.

Сделать отдельные наборы:

- `ProfileOrdinateStation` - вертикальные линии на графике профиля.
- `TableValueStation` - точки, где пишутся отметки в таблице.
- `UnfoldedPlanStation` - элементы развернутого плана.
- `PipeSlopeSegment` - прямолинейные участки трубы для строки уклонов.

Правила:

- В таблицу не добавлять каждые 20 м.
- В таблицу не добавлять `TIN-edge`.
- В таблицу добавлять начало, конец, УП, начало/конец футляра, пересечения, переломы проектной трубы.
- Пикеты 100 м (`ПК1`, `ПК2`) показывать только в развернутом плане.
- Для слишком близких точек применять дорожки/смещения, но не удалять инженерно важные точки.

Результат: таблица содержит меньше колонок, но профильные ординаты могут оставаться полными.

Кодовый объем сессии:

- выделить модели станций рядом с текущим кодом команд или в отдельный сервис;
- заменить общий список `TableStation` на отдельные списки для таблицы, графика, развернутого плана и уклонов;
- сохранить обратную совместимость `GREC` с уже построенными профилями.

Фактически сделано:

- `GREC` использует отдельные наборы `TableValueStation`, `PipeSlopeSegment` и станции развернутого плана;
- `GASPROF_DRAW_DRAFT` строит табличные станции отдельно от станций развернутого плана и сегментов уклонов;
- станции TIN/земли больше не попадают в таблицу как отдельный источник колонок;
- строка уклонов получает сегменты проектной трубы, а не общий список станций таблицы.

## Сессия 2. Вертикальные значения

Статус: реализовано в коде MVP.

Задача: привести числовые строки к виду ГОСТ.

Для строк:

- `Отметка земли проектная, м`
- `Отметка земли фактическая, м`
- `Отметка дна траншеи, м`
- `Отметка верха трубы, м`
- `Глубина траншеи, м`
- `Пикет`

Сделать:

- значения вертикальным текстом;
- якорь значения у соответствующей ординаты;
- разные вертикальные смещения для плотных соседних значений;
- формат пикета в строке `Пикет`: не `ПК0+16.50`, а `+16.50` внутри текущего пикета, а сам `ПК0`, `ПК1` отдельной меткой.

Результат: цифры перестают налезать горизонтально.

Кодовый объем сессии:

- добавить общий helper для вертикального текста в ячейках таблицы;
- реализовать дорожки/смещения для близких значений;
- вынести форматирование пикетажа для строки `Пикет` отдельно от полного формата `ПК0+00.00`.

Фактически сделано:

- значения в строках отметок земли, дна траншеи, верха трубы, глубины траншеи и пикета выводятся вертикально;
- строка `Пикет` использует компактный формат: `ПК0`, `ПК1` на сотнях и `+14.04` для промежуточных точек;
- один helper вертикального табличного значения добавлен в `GASPROF_DRAW_DRAFT` и `GREC`;
- для плотных соседних значений добавлены дорожки горизонтального смещения, чтобы близкие вертикальные подписи не вставали в одну линию.

Осталось после визуальной проверки:

- при необходимости скорректировать величину смещения дорожек и якорь текста после проверки в nanoCAD.

## Сессия 3. Объединенные строки

Статус: реализовано в коде MVP.

Задача: убрать лишнюю решетку.

Строки:

- `Обозначение трубы и тип изоляции`
- `Основание`

Сделать как объединенные по участкам:

- вертикальные линии станций через эти строки не проводить;
- подпись трубы рисовать один раз на участок одинакового типа;
- подпись основания рисовать один раз;
- оставить границы слева/справа и горизонтальные линии.

Текущий MVP:

- один участок трубы на всю трассу;
- одно основание на всю трассу;
- позже расширить на смену диаметра/изоляции по пикетажу.

Результат: середина таблицы выглядит как ГОСТ, а не как мелкая сетка.

Кодовый объем сессии:

- научить рендер таблицы рисовать вертикальные линии не через все строки, а по маске строк;
- добавить понятие `TableSpan` для участков одинаковой трубы/изоляции/основания;
- оставить MVP с одним участком на всю трассу.

Фактически сделано:

- вертикальные линии табличных станций рисуются составными сегментами;
- строки `Обозначение трубы и тип изоляции` и `Основание` пропускаются вертикальной сеткой станций;
- подпись трубы и подпись основания остаются одной общей подписью на всю трассу в `GASPROF_DRAW_DRAFT` и `GREC`.

Осталось после визуальной проверки:

- при необходимости поднять/сдвинуть текст span-строк;
- позже добавить настоящий `TableSpan`, если появится смена диаметра, изоляции или основания по трассе.

## Сессия 4. Строка уклонов

Статус: реализовано в коде MVP.

Задача: сделать строку `Уклон, промилле; длина, м` как в ГОСТ.

Сделать:

- ячейки уклона строить по прямолинейным участкам проектной трубы, а не по всем таблицам;
- вертикальные границы строки уклонов проводить только в точках перелома трубы;
- диагональ внутри ячейки;
- уклон над диагональю;
- длина под диагональю;
- если участок слишком короткий, подписи выносить в соседнюю дорожку или пропускать с предупреждением в `GVAL`.

Результат: строка уклонов читается как в примере Б.1.

Кодовый объем сессии:

- вычислять `PipeSlopeSegment` по вершинам проектной трубы;
- рисовать границы строки уклона только по концам сегментов;
- связать предупреждения о коротких сегментах с будущим `GVAL`.

Фактически сделано:

- `PipeSlopeSegment` строится по проектным точкам трубы в `GASPROF_DRAW_DRAFT` и по текущей отредактированной трубе в `GREC`;
- общие табличные станции больше не режут строку уклонов;
- вертикальные границы строки уклонов рисуются отдельно по началу и концу каждого сегмента трубы;
- диагональ в ячейке сохраняет направление уклона, уклон выводится над диагональю, длина под диагональю.

Осталось после визуальной проверки:

- настроить вынос/пропуск подписей для очень коротких сегментов;
- добавить предупреждения о коротких сегментах в `GVAL`.

## Сессия 5. Строки расстояний и пикетов

Статус: реализовано в коде MVP.

Задача: привести нижние строки таблицы.

`Расстояние, м`:

- расстояния писать между соседними `TableValueStation`;
- текст по центру интервала;
- не выводить слишком короткие интервалы как отдельную кашу, а объединять/смещать.

`Пикет`:

- показывать базовые пикеты `ПК0`, `ПК1`, `ПК2` вертикально;
- промежуточные точки подписывать как `+14.04`, `+18.68`;
- не дублировать полный пикет в каждой ячейке.

Результат: нижняя часть таблицы становится ближе к примеру.

Кодовый объем сессии:

- расстояния считать между соседними `TableValueStation`;
- отдельный formatter для базовых пикетов `ПК0`, `ПК1` и смещений `+14.04`;
- не использовать 20-метровые или 100-метровые пикеты как станции таблицы.

Фактически сделано:

- расстояния считаются между соседними `TableValueStation`;
- подпись расстояния центрируется по интервалу;
- для коротких интервалов применяется уменьшенный текст и две дорожки внутри строки;
- слишком короткие интервалы не подписываются в MVP, чтобы не создавать наложения;
- строка `Пикет` использует компактный formatter: `ПК0`, `ПК1` на сотнях и `+14.04` для промежуточных станций.

Осталось после визуальной проверки:

- добавить предупреждения в `GVAL` по пропущенным слишком коротким расстояниям;
- при необходимости вынести подписи очень коротких расстояний наружу.

## Сессия 6. Развернутый план

Статус: реализовано в коде MVP.

Задача: сделать развернутый план условной схемой, а не списком подписей.

Сделать:

- ось трассы толстой/основной линией внутри строки;
- УП показывать углом/ломаной или маркером с подписью `УП1`;
- футляр показывать как две параллельные линии/скобу с подписью `Футляр Ø...; L=...`;
- контрольную трубку показывать малым кружком;
- пикеты `ПК1`, `ПК2` показывать только здесь;
- подписи длины участков и углов поворота размещать как в примере.

Результат: строка развернутого плана становится самостоятельной пикетной схемой.

Кодовый объем сессии:

- создать/выделить `UnfoldedPlanRenderer`;
- футляр рисовать по началу/концу, а не как одну точку;
- использовать параметры футляра из планового блока и его актуализированных атрибутов;
- `ПК1`, `ПК2` показывать здесь, но не в таблице.

Фактически сделано:

- `GASPROF_DRAW_DRAFT` и `GREC` рисуют ось трассы в строке развернутого плана;
- УП получают отдельный маркер перелома рядом с подписью `УП1`, `УП2` и т. д.;
- 100-метровые пикеты остаются элементами развернутого плана, а не табличными станциями;
- футляр рисуется по фактическим `START_CHAINAGE`/`END_CHAINAGE` как протяженный элемент из двух параллельных линий с торцевыми перемычками;
- контрольная трубка футляра показана малым кружком на схеме;
- подпись футляра содержит длину, а под элементом выводятся пикеты начала и конца;
- при `GREC` футляр заново читается из актуальных атрибутов планового блока и не деградирует до одиночной точки.

Осталось после визуальной проверки:

- уточнить размеры условного знака футляра и контрольной трубки после проверки в nanoCAD;
- позже добавить реальные углы поворота в развернутый план, а не только маркер `УП`;
- после сессии типов линий назначить основной вес оси трассы и тонкий вес условных элементов.

## Сессия 8. Типы линий и толщины

Осталось после визуальной проверки:

- уточнить конкретные веса после печатной/видовой проверки в nanoCAD;
- позже вынести настройки весов в `GSET`, чтобы их можно было менять без пересборки DLL.

## Сессия 9. Настройки профиля

Статус: реализовано в коде MVP.

Задача: убрать хардкод.

Сделать команду, например `GSET` / `GASPROF_SETTINGS`:

- горизонтальный масштаб;
- вертикальный масштаб;
- глубина до верха трубы;
- наружный диаметр;
- толщина песчаной подушки;
- подпись трубы;
- подпись основания;
- режим отбора станций таблицы;
- минимальный зазор между подписями.

Сохранять настройки в XData профиля.

Результат: один профиль можно настраивать без пересборки DLL.

Кодовый объем сессии:

- расширить XData или extension dictionary профиля;
- сохранить глубину до верха трубы, диаметр, подушку, подписи, высоты текста и режимы станций;
- обеспечить чтение старых профилей с дефолтами.

Фактически сделано:

- добавлена команда `GASPROF_SETTINGS` и короткий алиас `GSET`;
- настройки профиля сохраняются в XData проектной трубы версии `GASPROF_PIPE_PROFILE_V5`;
- сохранены наружный диаметр, толщина песчаной подушки, подпись трубы и подпись основания;
- `GASPROF_DRAW_DRAFT` запрашивает песчаную подушку и подписи при первичном построении;
- `GREC` использует сохраненную толщину песчаной подушки и подписи при пересчете таблицы;
- старые профили `V1`-`V4` читаются с дефолтами;
- команды `GASPROF_ABOUT` и стартовое сообщение `NETLOAD` обновлены с учетом `GSET`.

Ограничение MVP:

- горизонтальный и вертикальный масштаб пока только читаются из метаданных, но не меняются через `GSET`, потому что изменение масштаба уже построенного профиля требует геометрического преобразования проектной трубы, таблицы, развернутого плана и графической ситуации.

## Сессия 10. Валидация UI

Статус: реализовано в коде MVP.

Задача: команда проверки оформления.

`GVAL` должна проверять:

- слишком плотные таблицы;
- пересекающиеся подписи;
- короткие сегменты уклонов;
- отсутствующий диаметр трубы;
- устаревшие футляры;
- отсутствие связи профиля с трассой;
- точки вне TIN.

Результат: перед выдачей можно понять, что именно надо поправить.

Кодовый объем сессии:

- расширить `GVAL` проверками UI;
- выводить понятные сообщения с пикетажем проблемного места;
- не запрещать построение при предупреждениях, но помечать риски оформления.

Фактически сделано:

- `GVAL` выводит сводку ошибок и предупреждений отдельным блоком;
- проверяется плотность табличных колонок по расчетной ширине в единицах чертежа;
- проверяются короткие сегменты строки уклонов и участки с уклоном больше 150 промилле;
- проверяются пустые/некорректные настройки профиля: диаметр, песчаная подушка, подпись трубы, подпись основания;
- проверяются изменения трассы, поверхности и проектной трубы по сигнатурам;
- проверяются футляры без пикетажа, без `GEOM_SIGNATURE` и с устаревшей сигнатурой;
- предупреждения содержат пикетаж проблемного места, где его можно определить;
- команда не блокирует построение, а сообщает, что нужно поправить или пересчитать перед выдачей.

## Порядок работы

Правильный порядок реализации:

1. Сессия 1: разделить станции.
2. Сессия 2: вертикальные значения.
3. Сессия 3: объединенные строки.
4. Сессия 4: строка уклонов.
5. Сессия 5: расстояния и пикеты.
6. Сессия 6: развернутый план.
7. Сессия 8: типы линий и толщины.
8. Сессия 7: элементы профиля.
9. Сессия 9: настройки.
10. Сессия 10: валидация - выполнено в MVP.

Ближайшая сессия для кода: следующая фаза после базового ГОСТ UI - **условная графика и UX плановой ситуации**. Главный риск теперь не расчет таблицы, а удобство создания/редактирования футляров и пересечений с последующим корректным отображением на профиле.
