# Концепция библиотеки блоков для профиля газопровода

## Общий подход

Для первой версии плагина не стоит делать сложные динамические блоки.

Лучший инженерный вариант:

- на плане хранить простые системные блоки с атрибутами;
- на профиле и в строке `Развернутый план` строить производную графику из этих атрибутов;
- сложную условную графику добавлять позже, когда расчетная часть будет стабильной.

Причина: динамический блок удобен для ручного черчения, но сложнее для надежного чтения и обновления плагином. Для расчетного плагина важнее стабильные атрибуты и предсказуемое имя блока.

## Принцип разделения

Нужно различать три сущности:

1. Блок на плане.
2. Отображение объекта на графике профиля.
3. Отображение объекта в строке `Развернутый план`.

Блок на плане является источником данных. Объекты на профиле являются производными и могут удаляться/перестраиваться командой `GASPROF_RECALC`.

## Блоки на плане

### `GASPROF_CROSSING_POINT`

Универсальный блок пересечения.

Графика:

- маленький круг;
- центр круга является расчетной точкой вставки;
- рядом допускается короткая подпись, но основная информация хранится в атрибутах.

Атрибуты:

```text
GP_TYPE
GP_NAME
GP_ELEVATION_TOP
GP_ELEVATION_BOTTOM
GP_DIAMETER
GP_WIDTH
GP_MATERIAL
GP_NOTE
GP_CHAINAGE
GP_PROFILE_ID
```

Типы `GP_TYPE`:

```text
ROAD
DITCH
WATER
SEWER
STORM
CABLE
COMMUNICATION
HEAT
GAS
RAIL
TRAM
CASE
OTHER
```

Этот блок закрывает большинство пересечений без отдельной библиотеки условных знаков.

### `GASPROF_PIPE_NODE`

Элемент проектируемого газопровода на плане.

Типы:

```text
GK      колодец
KV      ковер
KIP     контрольно-измерительный пункт
EIS     электроизолирующее соединение
UPEHZ   установка электрохимической защиты
VALVE   арматура
TIEIN   врезка
OTHER   прочее
```

Атрибуты:

```text
GP_TYPE
GP_NAME
GP_CHAINAGE
GP_ELEVATION
GP_NOTE
GP_PROFILE_ID
```

### `GASPROF_CASE`

Футляр на газопроводе.

Графика на плане:

- можно использовать маленький круг в начале футляра и атрибуты;
- либо два блока `CASE_START` / `CASE_END`;
- для MVP проще хранить один блок с длиной и пикетажем начала.

Атрибуты:

```text
GP_NAME
GP_CHAINAGE_START
GP_CHAINAGE_END
GP_LENGTH
GP_DIAMETER
GP_WALL
GP_MATERIAL
GP_NOTE
GP_PROFILE_ID
```

## Отображение на профиле

Плагин должен строить графику профиля сам, а не вставлять туда исходный плановый блок.

Для коммуникаций:

- вертикальная линия в пикетаже пересечения;
- упрощенный контур по габариту;
- подпись типа сети;
- отметка верха/низа, если задана;
- диаметр или ширина.

Для дорог/кюветов:

- контур или вертикальные границы пересечения;
- ширина;
- подпись;
- при необходимости футляр.

Для элементов газопровода:

- условный знак на линии трубы;
- выноска;
- подпись `ГК1`, `УП1`, `КИП`, `врезка` и т.п.

## Отображение в строке `Развернутый план`

Строка `Развернутый план` должна быть пикетной схемой, а не настоящим планом в координатах.

Показывать:

- ось газопровода горизонтальной линией;
- углы поворота как излом/стрелку/угловой знак;
- подписи `УП1`, `УП2`;
- значения углов поворота;
- футляры как параллельную линию или скобку с подписью;
- колодцы/коверы/КИП кружком или простым знаком;
- пересечения коммуникаций коротким штрихом с подписью.

Для MVP достаточно простых примитивов:

- `Line`;
- `Circle`;
- `Polyline`;
- `DBText/MText`.

## Почему не динамические блоки в MVP

Динамические блоки не нужны для первой версии, потому что:

- nanoCAD/.NET может сложнее читать динамические параметры, чем обычные атрибуты;
- плагину нужно надежно пересчитывать пикетаж, отметки и таблицу, а не управлять ручной графикой;
- разные DWG-шаблоны и версии nanoCAD могут по-разному вести себя с динамическими блоками;
- производную графику профиля проще удалить и построить заново;
- простые блоки с атрибутами легче тестировать.

Динамические блоки можно добавить позже для ручного оформления, но не делать их ядром данных.

## Что можно сделать вместо динамических блоков

Использовать параметрический генератор графики.

Например, `GP_TYPE = WATER`:

- на плане блок остается маленьким кругом;
- на профиле плагин рисует условный знак водопровода;
- в развернутом плане плагин ставит короткий штрих и подпись `В1`;
- в таблице выводит отметки и габариты.

Такой подход дает поведение динамического блока, но управление остается в коде.

## Минимальная библиотека MVP

Для первой версии достаточно трех блоков:

```text
GASPROF_CROSSING_POINT
GASPROF_PIPE_NODE
GASPROF_CASE
```

И набора типов в атрибутах.

Это позволит покрыть:

- дороги;
- кюветы;
- водопровод;
- канализацию;
- кабели;
- связь;
- теплосети;
- пересекаемые газопроводы;
- футляры;
- колодцы;
- коверы;
- КИП;
- врезки;
- углы поворота.

## Вторая очередь

После стабилизации MVP можно добавить:

- красивые DWG-блоки условных обозначений для профиля;
- динамические блоки для ручного оформления;
- палитру вставки объектов;
- справочник типов сетей;
- автозаполнение атрибутов по выбранному типу;
- проверку минимальных расстояний между газопроводом и пересекаемыми коммуникациями;
- импорт пересечений из выбранных линий коммуникаций на плане.

## Рекомендация

Ядро данных должно опираться на обычные блоки с атрибутами, а не на динамические свойства блока.

Динамические блоки допустимы только как внешний слой оформления. Если динамический блок потеряет параметры или будет вставлен из другого шаблона, расчет профиля не должен ломаться.
